CyberLab copied event correction

Written by KISS. Validation run: October 12, 2026 (America/Los_Angeles). Issue #136.

CyberLab sometimes includes multiple copies of the same logged action in one event list. The importer now keeps the first copy when every field matches and a nonempty timestamp is present. A repeated command with a different timestamp or any different field remains. Records without a timestamp remain too.

Comparison ignores object field order, preserves array order and value types, and compares Decimal numbers without rounding. Each event list starts a fresh comparison. This assumes equal complete timestamped records are copies; a source with coarse timestamps could record two genuine actions identically.

Processing order: source records → remove exact copies → join continuation lines → parse commands → write database rows. Retained records keep their original source positions in their IDs.

Complete source scan

Re-read all 293 downloaded archives: 154,097,349 events in 24,985,786 outer entries. The known truncated January 29 archive used the existing recovery rule. The independent comparison used recursively typed values and unordered object fields. It found 380,922 extra records, including 18,962 command records. Of those, 18,961 would be selected by the importer.

The importer prefers original shell inputs over command-handler messages when a list contains both. One shell input can produce several process rows, so source-event and database-row counts differ.

Regression checks and replacement

All 27 impacted tests passed. The new regressions use actual gzip input and DuckDB output. Published June cases retain 4,997, 4,702, and 4,701 process rows; September automation retains 8,974. November copies, separate connections, cross-entry/file records, continuation handling, input preference, exact Decimal comparisons, untimed repetition, and truncated-file recovery are covered. Source excerpts preserve every field and original outer/event positions.

Every reachable branch in the new helpers ran under coverage. The defensive error for unsupported value types cannot occur through the JSON reader and is documented in the tests. Ruff, Python compilation, and whitespace checks passed. Separate reviews of production code and tests found no demonstrated issues.

After all row differences matched their source explanations, replaced CyberLab rows in the local database in one transaction. The transaction checked the old rows had not changed, checked all new rows against the fresh database, and preserved other datasets’ counts and completion markers. The previous CyberLab rows remain in tmp/issue136/comparison.duckdb as baseline_PROCESS_LAUNCHES and baseline_SHELL_INPUTS. The completion marker is true.
